# 設計メモ: 番号の役割分担(entry_code / slot_label / 申込番号)

状態: **方針決定(2026-11-15、ユーザーと合意)**。コードの変更はまだない。今のデータの持ち方のままで成り立つ方針で、まず運用とCSVの決まりとして扱う。

## 背景

今は、名簿を組み合わせ順に作り、entry_code が組み合わせの番号と同じになるように振っている。そのため、entry_code に次の2つの役割を兼ねさせていた。

- システムの中で組を見分ける番号
- 進行表・組み合わせ表に印刷し、現場で呼ぶ番号

一方、slot_label(Stage内の位置)を呼ぶ番号にすると、後のStageで番号が変わってしまう。現場では、後のStageでも予選の番号で組を呼びたい。どちらの番号に何を持たせるかがはっきりしていなかった。

## 現場の番号の付け方(ユーザーから聞いたこと)

- 進行表は、横にコート、縦に試合順を取ったマトリクスが多い。対戦は「1-2(3)」のように書き、( )の中が指定審判の番号。
- 番号は、**カテゴリの最初のStageで、グループをまたいで一意になるように**振る。グループごとに1から振り直すことはまずない(例: Aリーグ1〜4、Bリーグ5〜8)。
- **後のStageでも予選の番号で組を呼ぶ**ことが多い。
- トーナメントでは、各コート第1試合の審判を、組み合わせ表の上で番号を四角で囲んで示すことが多い。

## 決めたこと

| 番号 | 役割 | 範囲 |
|---|---|---|
| `Participant.entry_code` | **抽選番号**。進行表・組み合わせ表に印刷し、現場で呼ぶ番号。大会を通して組に付いて回る。 | カテゴリ内で一意(今の `unique_together = (category, entry_code)` のとおり) |
| `slot_label`(Stageの枠) | そのStageの中の位置。主にIsconyの中で使う。人が呼ぶ番号には使わない。 | Stage内 |
| 申込番号(将来) | 参加申し込みの受付番号。entry_code には持たせない。 | 将来の申込側 |

- entry_code は**名簿の行番号ではない**。名簿の並び順は `Participant.display_order` で決まるので、entry_code を抽選番号にしても、名簿はチームごとなど好きな順に並べられる。
- CSVや画面で、人が書いた番号(進行表の審判の番号など)を受け取るときは、まず entry_code として扱う。

## 将来の参加申し込み機能との関係

将来、チームの代表者が選手名を登録して申し込む仕組みを作りたい(時期未定)。そのときに今の決まりが邪魔にならないよう、次の線を引いておく。

- 申し込みは、Participant(出場枠)とは別の「申込」として持つ。申込番号や受付順は申込の側に付ける。
- 抽選の後に、申込から Participant を作り、そのとき entry_code(抽選番号)を付ける。今の運用(抽選が済んで進行表ができてからIsconyを準備する)と同じ順番になる。
- 申込と Participant のつながりは番号ではなく、Participant から申込への参照で持つ。抽選番号を振り直しても、申し込みとのつながりは崩れない。

### 未決(今決めなくてよい)

- Isconyの中で抽選まで行う場合は、抽選前に Participant を作ることになる。entry_code は空欄にできないので、申込を Participant に流し込むのを抽選後にするか、抽選前は仮の番号を許すかを決める必要がある。
