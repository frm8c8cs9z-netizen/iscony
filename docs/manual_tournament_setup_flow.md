# 手入力による大会作成・編集導線メモ

このメモは、`iscony` で CSV なしでも大会を組めるようにするための設計メモです。

現時点の実装は、参加者、Stage、リーグ枠、トーナメント枠、進行表の作成が CSV 取込に強く依存しています。
将来的には、CSV は初期投入の高速導線として残しつつ、画面操作だけでも大会を作成・修正できる状態を目指します。

## 基本方針

- 先に「新規作成」の自然な流れを設計し、その形に「編集」を寄せる。
- 編集画面を先に増やしすぎると、既存DBやCSV取込後の都合に引っ張られるため、新規作成フローを主軸にする。
- ただし、作成画面を実装する前に、参加者、所属、指定審判、表示設定など、画面設計に強く影響するDB前提を先に整理する。
- 通常操作と高度操作を分ける。
- 結果入力係と、組み合わせ・Stage・進行を変更できる係は分ける。
- `Stage` は内部概念として重要だが、画面では「予選」「決勝」「順位決定」「次の枠へ反映」など運営者に伝わる表現へ寄せる。
- CSV取込は「一括作成」、画面編集は「確認・微修正・当日対応」という関係にする。

## 実装前に固める足回り

新規作成・編集画面を作り始める前に、次の順で土台を固めます。

1. データ構造を先に決める。
   参加者、所属、短縮表示名、当日変更、指定審判、変更履歴、採点票テンプレート、表示ブロック設定は、あとから画面全体へ影響するため、画面実装より先にモデル方針を決めます。

2. DB更新の入口をサービス層へ寄せる。
   CSV取込、画面手入力、大会複製、後続Stage反映、スナップショット復元のどこから入っても、同じサービス処理で状態を変えられるようにします。

3. 画面は薄く作る。
   Viewはフォーム入力、権限確認、遷移だけを担当し、参加者変更や進行変更のような業務判断は `core.services` に置きます。

4. 履歴とスナップショットを同時に考える。
   新しいDB項目を追加したら、変更履歴、スナップショット保存、復元、CSV取込、複製の対象に含めるかを同時に確認します。

5. 最初の実装単位を小さくする。
   まずはカテゴリ単位の参加者管理と、参加者変更履歴の最小モデルを候補にします。
   その後、指定審判、Stage作成、リーグ/トーナメント枠作成、進行表編集へ広げます。

この順番にすると、CSV取込で作った大会と画面で作った大会が別物になりにくくなります。
また、結果入力係と構成管理者の権限分離も後から載せやすくなります。

## 作成画面の前に整理するDB前提

新規作成画面は、DBの持ち方に強く引っ張られます。
そのため、画面を先に作り込む前に、次の項目は先に方針を決めます。

### 参加者と所属

現在の `Participant` は、ペア単位の `organization` と `player1_name` / `player2_name` を持っています。
今後は、選手ごとの所属表示や短縮表示を扱うため、次の整理が必要です。

- 選手1、選手2それぞれに所属を持たせる。
- フルネームと短縮表示名を分けて持たせる。
- 同一チーム内に同姓がいる場合、短縮表示名で識別できるようにする。
- 都道府県、学校名、クラブ名など、複数の所属要素を表示できる設計を検討する。
- 現在のペア単位所属表示も、既存大会や簡易大会向けに維持する。

この変更は、リーグ表、トーナメント表、採点票PDF、公開表示、CSV取込、スナップショット復元に影響します。

### 当日変更と変更履歴

実運用では、当初エントリーしていたペアの片方だけが当日に変更になることがあります。
この場合、画面上は当日出場する選手で運用しつつ、もともとのエントリー情報も後から確認できる必要があります。

基本方針:

- 当初エントリーの選手/所属と、当日出場する選手/所属を分けて保持する。
- 変更有無は、手入力のフラグだけに頼らず、当初情報と当日情報の差分から判定できるようにする。
- リーグ表、トーナメント表、採点票PDF、公開表示では、当日変更があることを色、印、注記などで分かるようにする。
- 片方だけ変更、両方変更、所属のみ変更のような差分を扱えるようにする。

最終形としては、変更履歴モデルを持つ方針を検討します。
変更履歴では、誰が、いつ、どの項目を、何から何へ変えたか、変更理由やメモを残せるようにします。
これにより、当日の問い合わせ、誤修正の確認、復元時の判断がしやすくなります。

同じ考え方は、試合順やコート変更にも必要です。
進行表のドラッグアンドドロップや当日差し替えでは、現在の配置だけでなく、変更前後の進行枠、コート、試合順、対象試合、変更者、変更日時、理由を追えるようにします。

履歴として優先的に持つ対象:

- 参加者変更
- 結果修正
- 試合順・コート変更
- 後続Stageへの反映、消し戻し、再反映
- リーグ枠、トーナメント枠、進出元条件の変更
- CSV取込、再取込
- スナップショット復元

これらは、運営事故が起きたときに「いつ、誰が、何を変えたために今の状態になったか」を追うために必要です。
特に結果修正と後続Stage反映は、表面上は単なる入力変更に見えても、後続試合や順位に影響するため履歴対象にします。

初期実装では優先度を下げる対象:

- 採点票PDFの出力履歴
- QR/キー検索の利用履歴
- 単なる画面閲覧ログ

これらは監査や分析には使えますが、まずは大会運営上の事故原因を追う履歴を優先します。

変更履歴は、将来的に undo の土台にもできます。
ただし、履歴があるから常に戻せるわけではありません。
後続Stageに結果入力済みの試合がない、対象データが別操作で再変更されていない、復元先の枠や参加者が削除されていないなど、安全条件を満たす場合だけ、画面から取り消せるようにします。
条件を満たさない場合は、自動undoではなく、差分確認、手動判断、またはスナップショット復元へ誘導します。

### 指定審判

進行表には、試合ごとに指定審判を持てるようにします。

想定する指定方法:

- リーグ内で、その試合に出ていないペアを指定する。
- トーナメントの敗者審判を指定する。
- 任意の参加者、ペア、またはテキストメモで指定する。
- 指定なしも許容する。

指定審判は、まず `Participant` 参照を主軸にします。
リーグ内の空きペアや、トーナメントの敗者審判のように、既存参加者で表現できるものは参照で持たせます。
参照で表現しにくい本部審判、外部審判、当日メモのようなケースは、自由入力メモで逃がせるようにします。

指定審判は、進行表CSV、進行表作成画面、採点票PDF、公開進行表、将来の電子スコアシートに影響します。
そのため、進行表の手入力作成UIより先に、`Schedule` にどう持たせるかを整理します。

### 大会単位の運用設定

大会ごとに変わりやすい設定は、作成画面の初期値としても使います。

候補:

- 採点票テンプレート
- 参加者表示ブロックのデフォルト
- 優勝者表示ブロックのデフォルト
- トーナメントスコア色
- 自動Stage反映の有無
- 自動スナップショットの有無
- 公開表示の範囲

個別のリーグやトーナメントで上書きできる設定と、大会全体の標準値として持つ設定を分けます。

### 枠表示と進出元

`slot_label` / `entry_code` / `pair_code` の役割を、作成画面に入る前に整理します。

- `entry_code` は参加者や確定済み枠の表面に出すコードとして扱う。
- `slot_label` は未確定枠や進出元説明の表示名として扱う。
- `pair_code` は旧実装や内部表示で残っている箇所を確認し、標準導線からは減らす。
- `1-10勝者`、`1-10敗者`、`リーグA 1位`、`分割ブラケット1勝者` のような進出元条件は、参加者差し替えとは別の構造情報として扱う。

Byeの勝ち上がりは、単なる結果ではなく構造上必要な情報です。
CSV取込、大会複製、画面生成で `winner_id` が欠けないようにします。

## 想定する作成フロー

```text
大会作成
  -> カテゴリ作成
  -> 参加者登録
  -> Stage作成
  -> リーグ/トーナメント枠作成
  -> 試合生成
  -> 後続Stageへの進出元設定
  -> 進行表作成
  -> 採点票・公開表示・運営導線の確認
```

この順番を基本にすることで、あとから編集するときも同じ場所へ戻れるようにします。

## 画面候補

### 1. 大会作成

大会そのものの基本情報を作る画面です。

主な項目:

- 大会名
- 大会コード
- 開催日や日程区分
- 公開設定
- 採点票テンプレート
- リーグ表/トーナメント表の表示初期設定

編集時も同じ画面を使い、既存の大会設定画面へ寄せます。

### 2. カテゴリ作成

大会内のカテゴリを作る画面です。

主な項目:

- カテゴリ名
- 表示順
- 公開対象にするか
- 管理側で表示するか

カテゴリは、参加者、Stage、リーグ/トーナメント、進行表の親になります。
そのため、以降の画面は基本的にカテゴリを選んでから操作する形にします。

### 3. 参加者登録

カテゴリ内の参加者を登録・編集する画面です。

主な項目:

- エントリーコード
- 選手名
- 短縮表示名
- 所属
- 複数所属
- 表示順
- 棄権/リタイアなどの状態

将来的には、選手ごとに所属を持たせ、ペア全体の所属表示も大会ごとに調整できるようにします。
中学校の全国大会のように、都道府県、学校名、所属チームなど複数の表示要素が必要な大会を想定します。

### 4. Stage作成

カテゴリ内に予選、決勝、順位決定戦などのまとまりを作る画面です。

主な項目:

- Stageコード
- Stage名
- 種別
  - リーグ
  - トーナメント
- 表示順
- 公開表示での扱い
- 管理表示での扱い

Stageは内部的には重要ですが、運営者向けには「どの結果が次のどこへ入るか」が分かる表示に寄せます。

### 5. リーグ作成

リーグStage内にグループと枠を作る画面です。

主な操作:

- グループ作成
- リーグ枠作成
- 参加者割当
- 表示ラベル設定
- 総当たり試合生成
- ゲーム数設定
- 順位計算方法の確認

編集時は、リーグ枠の参加者変更、棄権、表示順変更、試合再生成を扱います。
結果入力済みのリーグで試合再生成する場合は、必ず警告とスナップショットを挟みます。

### 6. トーナメント作成

トーナメントStage内にブラケット、枠、試合を作る画面です。

主な操作:

- ブラケット作成
- 出場枠数設定
- 枠ラベル設定
- 参加者割当
- 進出元割当
- シード/Bye設定
- 分割表示設定
- 試合生成
- ゲーム数設定
- 両山/片山表示設定

編集時は、次の3種類を明確に分けます。

- 枠の参加者を修正する
- 試合が参照する既存枠を選び替える
- 勝者/敗者/順位などの進出元条件そのものを修正する

現在の高度な編集は、既存の `TournamentEntry` を選び替える操作です。
`1-10勝者` を `1-10敗者` に変更するような操作は、進出元条件の編集として、この作成・編集導線で別途扱います。

### 7. 後続Stageへの進出元設定

前Stageの結果を、次Stageのどの枠へ入れるか設定する画面です。

主な対象:

- リーグの順位
- トーナメントの勝者
- トーナメントの敗者
- 分割ブラケットの勝者
- 手動指定枠

必要な考え方:

- 進出元が確定したら自動反映できるようにする。
- 反映元を修正した場合は、自動反映済みの後続枠を消し戻す。
- 後続側に結果入力済みの試合がある場合は自動消去せず警告する。
- 進出元条件そのものを変える操作は危険なので、構成管理権限側に置く。

### 8. 進行表作成

試合を日程区分、コート、試合順へ配置する画面です。

主な操作:

- 進行枠作成
- コート作成
- リーグ試合の配置
- トーナメント試合の配置
- 未配置試合の追加
- 試合順変更
- コート変更
- ドラッグアンドドロップによる入れ替え

結果入力済み、試合中、完了済みの試合は、移動や削除に制約をかけます。
進行表の変更は当日の混乱につながりやすいため、変更前スナップショットや確認ダイアログを組み合わせます。

## 編集導線の考え方

新規作成画面をベースに、編集も同じ文脈で扱います。

例:

- 参加者を追加したい
  - `カテゴリ -> 参加者登録`
- 参加者名や所属を直したい
  - `カテゴリ -> 参加者登録 -> 編集`
- トーナメントの枠に入る参加者を変えたい
  - `トーナメント作成/編集 -> 枠の参加者を修正`
- `1-10勝者` と `1-10敗者` を間違えていた
  - `後続Stageへの進出元設定 -> 進出元条件を修正`
- 試合順を変えたい
  - `進行表作成/編集 -> 試合順変更`

結果入力画面から大会構造を直接変更する導線は置かない方針です。
結果入力係が参加者違いや組み合わせ違いに気づいた場合は、保存せず構成管理者へ引き継ぐ導線を検討します。

## CSV取込との関係

CSV取込は今後も重要です。
特に大規模大会では、参加者や枠を画面だけで作るのは現実的ではありません。

ただし、標準導線は次のように整理します。

- CSV取込
  - 初期投入
  - 大量登録
  - 既存表計算ファイルからの投入
- 画面作成・編集
  - 小規模大会の作成
  - CSV取込後の確認
  - 当日変更
  - 部分修正

CSV再取込をしないと直せない状態は減らします。
一方で、進行済み・結果入力済みのデータを壊す可能性がある操作は、画面上で明確に警告します。

## 権限分離

将来的には、少なくとも次の役割を分けます。

- 大会オーナー
  - 大会設定、カテゴリ、参加者、Stage、リーグ/トーナメント枠、進行表、CSV取込、スナップショット復元を操作できる。
- 構成管理者
  - 参加者、組み合わせ、進出元条件、進行表を修正できる。
- 当日オペレーター
  - 結果入力、呼出、試合中、完了、採点票出力を操作できる。
- 閲覧のみ
  - 公開表示や確認画面だけを閲覧できる。

構成を変える操作は、必要に応じて都度パスワード確認や確認ダイアログを挟みます。

## 実装順の候補

### 第1段階: 設計を固定する

- このメモを土台に画面一覧を整理する。
- 既存メニューの中で、新規作成/編集導線に吸収する予定の画面を分類する。
- 「通常操作」「高度操作」「未実装の構成編集」を画面文言で分ける。

### 第2段階: 参加者管理

- カテゴリ単位の参加者一覧を作る。
- 参加者の新規作成・編集を作る。
- 短縮表示名、所属表示の拡張に備えた項目整理を始める。

### 第3段階: Stage管理

- カテゴリ内のStage一覧を、作成/編集できる画面にする。
- Stage名、種別、表示順、公開/管理表示を編集できるようにする。

### 第4段階: 枠作成

- リーグ枠作成・編集。
- トーナメント枠作成・編集。
- 進出元条件の作成・編集。

### 第5段階: 試合生成

- リーグの総当たり試合生成。
- トーナメント試合生成。
- 既存結果がある場合の再生成制約。

### 第6段階: 進行表編集

- 未配置試合の配置。
- コート/試合順の移動。
- ドラッグアンドドロップ。

## 保留・要検討

- 参加者の複数所属をどのモデルで持つか。
- 短縮表示名を `Participant` に持たせるか、表示設定側で持つか。
- `LeagueEntry` / `TournamentEntry` の表示用重複列をいつ削るか。
- `slot_label` / `entry_code` / `pair_code` の画面上の役割整理。
- Byeの `winner_id` を結果ではなく構造情報として扱う範囲。
- 進出元条件編集後に、既存の後続反映や結果をどこまで自動で消し戻すか。
- 構成管理操作をどの権限に置くか。
