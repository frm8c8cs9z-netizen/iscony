# 大会の所有者と当日担当

## 背景

- 今は、一般公開の画面以外はすべてログインが必要。
- ログインした人は、どの大会のどの操作でもできる。大会に所有者の項目はない。
- 大会ごとに一般公開用の推測されにくい文字列(`public_token`)はあるが、運営用の別の入口はない。
- 12/19 の反応次第で、他の主催者に渡すかどうかを決める。
- 将来はコードを公開する予定。

## 利用者の分け方

| 区分 | 誰 | 入り方 | どこに属するか |
|---|---|---|---|
| 運営側 | 所有者・共同管理者 | iscony 全体のアカウントでログイン(今のログイン) | iscony 全体 |
| 大会ごとの利用者 | 当日担当 | 担当者用 URL + パスコード(アカウントなし) | その大会の中だけ |
| 大会ごとの利用者 | エントリーする監督・選手 | その大会の申込ページで登録 | その大会の中だけ。`docs/design_entry_system.md` |
| 観客 | 一般 | 公開 URL(ログインなし) | — |

運営側のアカウントと、大会ごとの利用者は別の仕組みにする。

## 所有者・共同管理者

- 大会ごとに管理者の一覧(人、役割)を持たせる。
  - 役割は「所有者」と「共同管理者」。
  - 大会に所有者の欄を1つ持たせるのではなく、一覧にする。共同管理者を足せるようにするため。
- 共同管理者は、大会の操作をすべてできる。
- 所有者だけができることは、次の2つ。
  - 大会の削除。
  - 共同管理者の追加と削除。
- 最初は、所有者がすでにあるアカウントを指名して共同管理者にする。
  - アカウントは、今どおり管理画面(`isconyadm/`)で作る。
- 今ある大会は、今のユーザーの所有にする。

## 当日担当

- 係(担当者の種類)を、大会ごとに複数持てるようにする。
  - 最初のうちは、実際に使う係は1つの想定。
  - [AGENTS.md](../AGENTS.md) の「結果入力係と、組み合わせやStageを変更できる係は分ける」は、係を分けることで表せる。
- 係ごとに次のものを持つ。
  - 名前
  - 担当者用 URL(推測されにくい文字列)
  - パスコード
  - 許可する操作
- 担当者用 URL を開くとパスコードを聞く。正しければ、その端末をその大会のその係として扱う。
  - ログインは不要。
  - 他の大会や管理メニューには入れない。
- 許可する操作は、所有者・共同管理者がその場でオン・オフできる。
  - 操作のたびに判定するので、オフにした時点で、すでに入っている端末からも使えなくなる。
- パスコードを変える、または URL を作り直すと、それまで入っていた端末はすべて入り直しになる。
- 安全面:
  - パスコードはそのまま保存しない(ハッシュで保存する)。
  - 続けて間違えたら、しばらく受け付けない。
  - URL とパスコードの両方がそろわないと入れない。
- 許可する操作の候補: 結果入力、QR/キー検索、進行表の閲覧、試合移動、当日追加(リーグ・トーナメント)、本部コメント、印刷。
